## Context

ACM-009 (RF-1, tier/enchant selectors) requires `item.maxEnchant` (see its AC#2)
so the editor can render an enchant select showing `0..item.maxEnchant`. The
current implementation in `src/components/editor/tier-enchant.ts` instead
parses an `@0`-`@4` suffix off `AOItem.uniquename`. Code review of PR #16
found this unimplementable: the real fixture corpus
(`src/__tests__/fixtures/ao-corpus.json`, 2036 items generated by the
ACM-002/003/004 pipeline) has zero items with `@` in `uniquename`, and
`AOItem` (src/data/ao-data.d.ts) has no `maxEnchant` field. The existing unit
test only passed because it used a fabricated id
(`T8_HEAD_PLATE_SET1@1`) that does not occur in real data.

I verified the current upstream schema directly (ao-bin-dumps was
restructured; ACM-024/025/026 already had to adapt to it, so memory of the
old schema cannot be trusted). I downloaded the current
`items.json` (raw game item defs, 17MB, `.../ao-bin-dumps/master/items.json`)
and inspected `equipmentitem`, `weapon`, `mount`, `transformationweapon`
categories:

- Enchantment is represented as a nested `enchantments.enchantment` array on
  the BASE item record, one entry per enchant level (`@enchantmentlevel`
  1..N), not as separate items with an `@N` uniquename suffix. Zero items in
  any equippable category have `@` in `@uniquename` — the `@N` suffix
  convention does not exist in this upstream source at all.
- Distribution of enchant levels observed (max `@enchantmentlevel` present,
  or 0 if `enchantments` key absent):
  - `equipmentitem`: 425 items with 0, 724 items with 4
  - `weapon`: 126 with 0, 5 with 3, 640 with 4
  - `mount`: all 109 with 0 (mounts are not enchantable)
  - `transformationweapon`: 1 with 0, 40 with 4
  - So `maxEnchant` is a small integer, empirically always 0, 3, or 4 — never
    derivable from a fixed constant, must be read per item.
- The `enchantment` child nodes carry crafting/upgrade cost data
  (`craftingrequirements`, `upgraderequirements`) and stat deltas
  (`@itempower`, `@durability`), but never spell references. Spells are
  resolved once per base item via `craftingspelllist` / the existing
  spell-resolver chain (ACM-003) and do not vary by enchant level. This
  confirms `resolveSpells` does not need to change.
- Tier (`T1`-`T8` uniquename prefix) is a separate, correctly-modeled axis
  and is unaffected by this decision.

## Decision

The data pipeline (`scripts/sync-ao-data.ts`) will emit a `maxEnchant: number`
field on `AOItem`, computed as the count of `enchantments.enchantment` entries
on the raw item record (0 when the `enchantments` key is absent). This follows
the same pattern as decision-004 / ACM-026 (`twohanded`): read a real
upstream attribute into a typed field, rather than inferring state from
`uniquename` string parsing.

Options considered:
1. **Emit `maxEnchant` from `enchantments.enchantment` length (chosen).**
   Matches the real upstream shape, zero ambiguity, cheap to compute during
   the existing per-item emit loop (the raw item record is already in scope
   in `sync-ao-data.ts`).
2. **Emit explicit enchanted item variants (`T4_HEAD_PLATE_SET1@1` as a
   separate `AOItem`).** Rejected: upstream doesn't model it this way, so
   we'd be inventing ids that don't correspond to any real uniquename,
   re-introducing exactly the fabricated-fixture problem found in review.
   Also multiplies item count ~4x for no benefit since spells/slot/tier
   are identical across enchant levels of the same base item.
3. **Descope enchant entirely from v1, drop the `◆N` badge.** Rejected:
   PRD RF-1 and the build card (ACM-011/ACM-013) already require an enchant
   badge; removing it is a product regression, not just a data-modeling
   choice, and the fix (option 1) is cheap.

## Consequences

- New task required to implement the pipeline change (file scope: `scripts/`
  + `src/data/` + their tests) before ACM-009 AC#2 can be correctly
  implemented against real data.
- `tier-enchant.ts`'s `getEnchantOptions()` must be rewritten to read
  `item.maxEnchant` instead of parsing `uniquename`; its existing test using
  the fabricated `@1` id must be replaced with a real fixture item that has
  `maxEnchant > 0` (e.g. `T4_HEAD_PLATE_SET1`).
  the fixture corpus will need to be regenerated once the pipeline change
  lands.
- ACM-009 PR #16 should be descoped to tier-only for now (see task notes)
  rather than held, since AC#1 and AC#3 are implementable and reviewable
  independently of AC#2.
