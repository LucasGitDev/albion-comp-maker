## Context

ACM-013 requires `BuildCard` to be the single source of truth for both the on-screen
preview and the exported PNG (RF-4/RF-5, AC#4). Two approaches were considered to make
"same React tree" actually true in practice:

1. A `mode="preview" | "export"` prop with conditionals inside `BuildCard` toggling hover
   affordances, tooltips, focus rings, and the clear/swap buttons on or off.
2. Cloning the DOM node at export time and stripping interactive chrome from the clone
   before rasterizing.
3. `BuildCard` never renders interactive chrome at all — it is a pure, prop-driven capture
   root (`#capture-root`) with zero buttons/inputs/hover styles. All editor-only affordances
   (hover highlight, "×" clear button, tooltips, focus rings) live in a sibling
   absolutely-positioned overlay component owned by the editor, never inside the card tree.

Option 1 was rejected: every conditional branch is a chance for preview and export to
silently diverge — exactly the bug class this task exists to prevent, and it would be
invisible until a user's exported PNG showed a stray hover state or missing content.

Option 2 was rejected: cloning loses computed styles that were only applied via
in-browser interaction state (`:hover`, `:focus`), which is the same category of
export/preview divergence as option 1, plus extra runtime complexity.

## Decision

`BuildCard` (and everything under `src/components/build-card/`) never imports a store,
never renders `<button>`/`<input>`/interactive elements, and never has `:hover`-only
styling. It is pure with respect to its props (`state: BuildState`, `theme`, name/spell
lookups). This is what ACM-015 (PNG export, decision-007, html-to-image) will capture
directly via `toPng(document.getElementById('capture-root'))` with no parallel render
path. The exported card also never renders empty equipment slots (draft/dashed slots make
sense in the editor as an invitation to fill them; they read as a rendering bug in a PNG).

Editor-only affordances (hover highlight matching a slot, "×" clear button, tooltips with
full item/spell names, focus rings) belong to a sibling overlay component that the editor
page renders positioned on top of `BuildCard`, keyed off the same `slot` identifiers
(`data-slot="..."` attributes on `CardSlotTile`). That overlay is out of scope for
ACM-013 — it belongs to whichever task wires `BuildCard` into the interactive editor.

Every color inside `build-card/**` is a hex literal (`src/components/build-card/tokens.ts`)
or an inline hex `style` value, never a Tailwind default-palette utility class (those
compile to `oklch()` in Tailwind v4, which html-to-image's SVG-foreignObject rasterizer
cannot parse — see decision-007).

## Consequences

- The acceptance test for AC#4 becomes mechanical: capturing the same `#capture-root` node
  with the mouse over a slot vs. off-window must produce byte-identical output, because
  there is no hover-reactive markup inside the node to begin with. `src/__tests__/build-card.test.tsx`
  approximates this by rendering the same `BuildState` twice and asserting identical HTML.
- Any future feature that wants to show something conditionally in the export (e.g. a
  watermark, a "generated by" footer) must be an unconditional part of `BuildCard`'s own
  render output, not a prop-toggled branch reacting to interaction state.
- The editor's overlay component (hover ring, clear button, tooltips) is a separate,
  non-trivial piece of follow-up work; it was deliberately not built in ACM-013 to keep
  this task's scope to the capture root itself.
- `BuildCard` has no dependency on Zustand or React context, so it can later be rendered
  server-side or through Satori (ACM-021/ACM-022) without a second implementation.
