# Decision: PNG export library choice

## Status
Accepted

## Context
ACM-015 requires client-side export of the build card preview component (ACM-013) to a
Discord-ready PNG, plus copy-to-clipboard. Constraints:

- No backend/server infra for rendering (out of scope for v1, no headless browser available
  in the Next.js app's runtime).
- The preview component IS the export component (ACM-013 AC#4) — same React tree is used
  for on-screen preview and for export, so whatever export mechanism we pick must operate on
  a live DOM node, not a re-rendered JSX tree.
- Icons are served through `/api/icon` (ACM-006, same-origin route), so cross-origin taint is
  avoidable as long as the export library does not re-fetch icons through a different path
  that bypasses same-origin caching/headers.
- Cards use Tailwind v4 utility classes, CSS custom properties for theme tokens (ACM-014),
  and potentially an uploaded background image (object storage URL).
- Output must be visually identical to on-screen preview (1:1), at high enough resolution to
  look sharp when re-uploaded to Discord.

## Options considered

1. **html2canvas** — mature, widely used, but effectively unmaintained (last major release
   years old) and has long-standing open issues with modern Tailwind (oklch/color-mix
   generated by Tailwind v4), CSS transforms/filters (used for background blur/darken in
   ACM-014), and `object-fit`. Known to silently drop styles rather than error, which is worse
   than a build failure for a visual export feature.

2. **dom-to-image-more** — actively maintained fork, similar architecture (serializes DOM to
   SVG `foreignObject`, then rasterizes to canvas). Same fundamental technique as html2canvas
   but with better maintenance and reported Tailwind v4 compatibility.

3. **html-to-image** — actively maintained, most-starred fork in this family, same
   SVG-foreignObject technique, has first-class `toPng`, `toBlob`, and `toCanvas` helpers,
   supports `pixelRatio` for high-DPI export, and `fontEmbedCSS`/`getFontEmbedCSS` to inline
   `@font-face` rules so exported PNGs don't depend on the browser having fonts loaded at
   rasterization time. Has an established pattern for `Clipboard.write` via `toBlob`.

4. **Playwright server-side screenshot** — most accurate (real browser layout engine) but
   requires a server/queue to run a headless browser, contradicting the "no backend, no DB"
   v1 scope and adding infra cost purely for a feature that must also support instant
   "Download" and "Copy" actions from the client without a round trip.

5. **Manual canvas drawing** — most control, but requires reimplementing layout, text
   wrapping, icon compositing, and theme presets in imperative canvas code, duplicating
   ACM-013's React tree. Directly violates ACM-013 AC#4 (single source of truth) and is not
   proportional effort for v1.

## Decision

Use **html-to-image** (`toPng` / `toBlob`) for ACM-015.

- Export the same DOM node rendered by the ACM-013 preview component — no parallel render
  path, satisfying ACM-013 AC#4.
- `pixelRatio: 2` for the Download button, per task spec, to get a sharp 2x export without
  inflating memory usage the way a very large `width`/`height` override would.
- Call `getFontEmbedCSS(node)` and pass it as `fontEmbedCSS` before rasterizing, so exported
  PNGs render the correct webfont even in browsers/timings where the font isn't rasterized
  in time — this satisfies AC#4 (webfonts embedded).
- Icons: since `/api/icon` is same-origin and sets a long-lived `Cache-Control` header
  (ACM-006), `html-to-image`'s internal `fetch`-based inlining of `<img>` sources will not hit
  CORS/tainted-canvas issues. No `crossOrigin` attribute workaround is required as long as
  icon `<img>` tags point at the same-origin `/api/icon` path (not directly at
  `render.albiononline.com`).
- Clipboard: use `toBlob()` output with `navigator.clipboard.write([new ClipboardItem({
  'image/png': blob })])`. This API is Chrome/Edge-only per the task's own AC#2; Safari/Firefox
  fallback (if ever needed) is out of scope for ACM-015 and should be a separate task if
  requested.
- If dom-to-image-more or html2canvas is later found necessary as a fallback for a specific
  browser bug, that is a follow-up decision, not a retrofit of this one.

## Consequences

- Export quality is bounded by the "serialize DOM to SVG, then rasterize" technique shared by
  this whole library family: complex CSS filters (background blur in ACM-014) must be tested
  explicitly, since `foreignObject`-based rendering has historically had partial support for
  `filter` in some browsers. This must be covered by a manual verification step in ACM-015's
  DoD, not assumed to work from the library's docs alone.
- Any uploaded background image (ACM-014) must be served from a same-origin or
  CORS-permissive URL, or export will silently omit it. If backgrounds are stored on external
  object storage, that storage's CORS policy must allow anonymous GET with
  `Access-Control-Allow-Origin` — flag this to whoever implements ACM-014's storage layer.
- No server dependency added; the export stays fully client-side, preserving v1's "no
  backend" scope for this feature.
